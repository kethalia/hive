# Local publication runtime proof

Run `node deploy/cloudflare/jobs/run-local-publication.mjs` after creating the private local PostgreSQL fixture recorded in `/tmp/hive-template-fixture.json`. No cloud deployment, cron, API credential, paid resource or remote database is involved. The runner uses the repository's installed Wrangler with `dev --local`, task-owned temporary configuration and secrets, and local-only service/ASSETS bindings.

The entrypoint imports the real full-schema generated workerd Prisma client and production database request lifetime. A fixed loopback-only WebSocket bridge carries PostgreSQL wire bytes to this task's local PostgreSQL 17 cluster. Each run creates a new `hive_template_workerd_<random>` database and applies the current migrations. This is not a replacement HTTP SQL emulator: interactive Serializable transactions, row locks, database clock, publication events and uncertainty state use real PostgreSQL.

Neon's ESM and CJS entrypoints keep independent global configuration. The local fixture explicitly configures the **ESM** entrypoint used by `@prisma/adapter-neon` to point at its fixed local bridge. Initial attempts configuring the directory/CJS main instead failed before reaching the bridge. This override exists only in the local test entrypoint; production driver configuration is unchanged. The pattern is based on [Neon's published non-Neon WebSocket configuration](https://github.com/neondatabase/serverless/blob/main/CONFIG.md). [Wrangler local mode](https://developers.cloudflare.com/workers/local-development/) disables remote bindings.

The production jobs dispatcher runs a disabled wake and a real enabled empty-queue claim using the Worker client; its HTTP handler returns 404. Positive publication effects run the real publication service and Coder provider protocol adapter with the jobs authentication-service buffering/authorizer and real ASSETS binding. Only the provider's transport is explicitly replaced with a **synthetic service binding** at an `.invalid` origin. The fake API records uploads/version creation/activation and can return an unknown version or activation response. No real Coder endpoint is contacted and no installed host or deployment is authorized by this proof.

The synthetic auth service returns a synthetic session/token that matches only new local fixture rows. No real key is decrypted, minted, rotated or persisted. The canonical artifact is built from a tracked `HEAD` template export, with metadata required to match both that commit's manifest and the working manifest. This excludes unrelated untracked template work while retaining exact committed bytes. `workerd.json` records the template commit, artifact digest and hashes of the tested working runtime sources; it does not claim an installed-template or remote-provider proof.

Acceptance covers one successful upload/import/activation; one ambiguous version creation followed by a missing identity readback and no second create; one ambiguous activation held despite the fake provider applying it; exact ASSETS digest and changed identity rejection; disabled jobs/browser paths; actual jobs HTTP 404; and omission of synthetic raw provisioner secrets from controller events.

The first actual ASSETS attempt exposed a real compatibility failure: Workers rejects `Request.redirect="error"`. The corrected source uses `manual`, rejects non-200/redirected responses, and bounds cancellation. The earlier failure is preserved in `workerd-failures.json`; private logs remain under the recorded `/tmp` path. This correction is separate from the local ESM/CJS proxy configuration issue.

The runner stops only its still-live child process group, never signals a numeric group after its leader is reaped, closes the fixed bridge and preserves uncertain/failing scratch directories. Successful scratch is removed after observed group absence; local databases and the PostgreSQL cluster are retained for parent review. The proof does not establish real-provider success, first-template creation, variables/README parity, detailed raw-log viewing, or cutover readiness. All deployment flags and crons remain off.
