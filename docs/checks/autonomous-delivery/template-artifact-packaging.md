# One template artifact for Node and Workers

The deployment's observed Coder upload ceiling remains **1,048,576 bytes**. The host
package keeps its separate **160,000-byte compressed / 2 MiB expanded** limits. This
change makes no deployment, policy, profile or cleanup-authority change.

`build-template-artifacts.mjs` verifies the bounded host gzip, its expanded tar SHA,
regular-file inventory and package-manifest file digests before considering any
loose runtime source redundant. Python must match its installed bytes exactly. JS
must match the exact esbuild transform used by `build-codex-host-bundle.mjs`, including
the existing fixed `ws` import rewrite. A stale or altered installed source rejects
the build. Unknown files remain in the template; no filename-only exclusion list is
used. Repository and profile sources remain unchanged by distribution filtering.

Terraform, shell/bootstrap and Python basename references retain candidate files;
retained JS sibling imports retain their dependencies. This runs to a fixed point.
There is **no Python-installer exemption**. Dynamic Terraform script selection and
script filesets require explicit packaging review instead of silently omitting an
input. Tests extract the actual archive and require every literal current
`${path.module}/...` Terraform input to exist. This conservative static check is not
a general interpreter for arbitrary future dynamically constructed paths; new such
bootstrap/provisioner behavior requires reviewing its distribution dependencies.

Including accepted-source application exceeded the gzip budget. The selected
change is esbuild `minifyWhitespace: true, minifyIdentifiers: true, keepNames: true,
minifySyntax: false`, for both canonical modules and locked ws, with the existing
Node24/ESM target. Runtime names are retained; syntax minification stays disabled.
Whitespace alone passed but left only 1,271 compressed bytes for upcoming reviewed
source-application wiring. Identifier compaction provides 8,422 bytes of headroom. Compiled
module bytes—not merely imports—are exercised by existing controller, bridge,
startup, native WS/CLI/child/resume and crash tests. A resolver maps only exact package
manifest module names. It asserts positive child-runner test counts and actual
module mappings; nested `NODE_TEST_CONTEXT` is removed to prevent an empty nested
Node test run being mistaken for validation.

Both runtimes now compare maintained templates against the same build manifest
content identity. `pnpm build` first verifies the manifest and writes the exact tar
assets to `public/hive-template-artifacts`, already copied by the Node image. Node
push reads at most the manifest size plus one byte, verifies size and SHA, then
sends that buffer to `coder templates push --directory -`; the installed Coder 2.38.2
help confirms stdin-tar support. It does not ask Coder to rescan a mutable directory.
Unknown templates and missing/altered assets reject before resolving an owner token
or spawning Coder. An input-pipe failure stays failed even if the child later exits0.
Ad-hoc Node staleness hashing remains for legacy callers, but maintained-template
pushes accept only the five known manifest entries.

## Validation and boundaries

Evidence is in `template-artifact-local/result.json` and adjacent logs. The clean
export uses HEAD plus the frozen accepted-source helper, factual state client and
this packaging slice. A second copy adds the frozen guardian-controller 20-path
slice and its new module to its **copy-only** bundle inventory. Unreviewed collector
or other concurrent working changes are excluded.

The assembled guardian copy measures **151,578 gzip bytes including the reviewed guardian ELF** and a maximum
**949,760-byte template tar**, below both existing limits. No primary template archive,
profile copy or generated manifest was regenerated by this agent. Parent assembly
must regenerate and verify them from the reviewed combined source before commit.

The actual fixed Python installer→FD3 outer→guardian→worker proof passed with compiled
modules, including exact listener identity, duplicate-launch refusal and denied
unapproved preparation. It uses its existing private user-namespace fixture and
reviewed CI ELF; no primary auth/home or live workspace was changed. The native
proof uses only local canned Responses, not account inference.

Two native fixture placement failures were retained: `/tmp` was rejected by the
existing real-home alias guard; an overly deep real-home export exceeded tmux's Unix
socket path budget. Moving the same export to a short task-owned path allowed all
three native namespace tests to pass. These are fixture placement limitations, not
claims of an application startup fix. The first draft nested runner produced empty
output; its validation was discarded and the harness now rejects that condition.

This is packaging/runtime compatibility evidence. It grants no source application,
model execution, writer quiescence or checkout deletion authority.
