# D11 coordination: local implementation checkpoint

The manager can submit a versioned decomposition bound to the independent owner acceptance plan. The scheduled project controller reserves the workspace and reviewed isolation domain before preparation; active reservations count against the plan's WIP limit. A started task cannot be changed by replanning. Dependency admission requires a healthy attributed release and GitHub compare evidence from its merge commit to the proposed input revision, including squash merges. The integration node covers every owner criterion and follows all implementation nodes.

Execution is disabled unless the existing project/manager/guardian gates and `HIVE_DELIVERY_EPICS_ENABLED` are enabled. `HIVE_DELIVERY_EPIC_ISOLATION_POLICY` is deployment-owned reviewed enrollment: schema version 1 and a `workspaces` array containing the Hive `ownerId`, `workspaceId`, current `buildId`, globally unique provisioner-assigned `isolationDomain` and millisecond `validUntil`. An isolation domain is an operator assertion about the reviewed template and PVC arrangement, not an inference from an inode or UUID. `HIVE_DELIVERY_EPIC_GITHUB_READ_TOKEN` is a separate read credential for bounded GitHub repository/commit comparison. Enrollment, bucket retention and credentials are rollout prerequisites; do not enable the feature merely because these fields can be configured.

A closed guardian tree is not itself permission to release a checkout. The outer controller first obtains current release evidence and a content-addressed R2 manifest with bounded event summaries, reports, evidence references, accepted source and local session identity. The retained local session is not represented as a remotely backed-up transcript. The controller releases only the matching managed checkout lease after tree exit, obtains a server-signed receipt bound to that lease and preservation, archives the managed source and task journal, then acknowledges archival. Only that acknowledgement releases the writer reservation and finishes the start reservation. Persistent and user-owned checkouts are not enrolled for managed deletion; this path does not delete them. A mixed epic/non-epic guardian inventory is retained for reconciliation. Lost acknowledgements retain or replay the same scoped journaled operation.

## Manager loop and current routing limits

The coordinating manager creates its owner-bound delivery task and calls `hive_delivery` operation `read_epic_context` with its task ID. The response contains the independently accepted criterion IDs and meanings, the current plan version and digest, eligible enrolled workspace IDs, and the supported model tiers. It then calls `plan_epic` with that version and digest, the WIP limit, and a bounded list of tasks. Each task provides a stable short key, enrolled workspace, exact input revision, task text, criterion IDs, dependency keys, implementation or integration role, and a supported tier. The controller derives request and intent IDs, binds the owner outcome and computes all digests. There is exactly one integration node, which follows every implementation node and covers all owner criteria. The coordinating task is separate from those nodes. The scheduler reserves and dispatches eligible nodes without individual task approval; blocked and uncertain work remains held. The manager can pause scheduling and re-read context before submitting a new chained plan. Started nodes remain fixed.

The default tier pins the deployment-configured `HIVE_CODEX_MANAGER_MODEL` and `HIVE_CODEX_MANAGER_EFFORT` pair. An operator can set `HIVE_DELIVERY_EPIC_MODEL_TIERS_JSON` to a reviewed JSON array of up to eight `{tier, model, effort}` entries; it must include that exact pair under `default`. The manager selects a named tier per task and the plan pins its pair. The coordinating host retains its enrolled manager settings; delegated child claims must request the pinned pair, and observed effective settings must match for completion. The scheduler holds nodes whose pinned pair no longer appears in the catalog. Account availability and actual multi-model execution still require an installed pilot. The legacy `write_epic_plan` operation remains available for exact versioned payloads, but normal manager use should prefer the bounded context and proposal operations.
