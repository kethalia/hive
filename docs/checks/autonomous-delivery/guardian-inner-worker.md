# Guardian inner software worker

Status: local integration candidate; installed defaults and all delivery pilot flags remain off. This extends the existing signed controller journal rather than introducing a second project authority. The outer launcher, installer startup attestation, controller drain authorization and server receipt ingestion remain separate boundaries.

The fixed no-argument `codex-workspace-host-worker.mjs` connects only through inherited FD3 and starts the existing software host. The legacy host CLI remains available and does not select a guardian implicitly. The guardian owns the whole Node worker tree, including bounded catalog helpers, checkout preparation, native namespace wrappers, tmux daemons and Python PTY clients. Pre-project catalog discovery is a read-only workspace operation; it cannot mint a project or checkout admission. Controller preparation is admitted before repository resolution, checkout inspection or Git helper execution. Pending catalog/project responses are rejected after closure.

The optional `guardianEnabled` configuration defaults to legacy behavior and requires native isolation when true. The legacy entry rejects a guardian-enabled configuration, and the guarded worker rejects an unguarded configuration. Startup metadata hashes the exact private bytes parsed once; the same parsed configuration starts the listener before the worker's separate ready handshake. Startup readiness grants no project execution. Until the independent server admission/barrier store is implemented, the installed outer composition must deny preparation and drain rather than trust its local journal as authorization.

## Durable records and fences

`projects.json` retains its HMAC signature, exclusive flock, atomic replacement and file/directory fsync. Guardian integration is supplied through trusted function dependencies, never HTTP fields or model commands.

A task records `guardianPreparation` before requesting admission. This immutable record pins owner, workspace, build, project, repository/provider account, task/request identity, base SHA and request digest. It deliberately contains no predicted lease or checkout incarnation. The ACK is retained as `guardianAdmission`, a historical receipt; an in-memory opaque FD-client token remains the execution authority. `guardianPrepared` is appended after preparation, before native enrollment, and separately pins the actual lease, generation and checkout incarnation to the original preparation digest. Neither record rewrites its predecessor.

Project admissions append to one lifetime. A newly admitted project changes the shared generation; existing opaque tokens are explicitly fenced again before shared helper/native work. Native RPCs, model tool replies and CLI launches assert admission at their actual write boundaries. Positive responses arriving after closure are discarded, preserving uncertain creation/reservation state. Existing signed registration, lease, child provenance, progression and lost-ACK holds continue to apply. A new guardian lifetime cannot adopt earlier controller execution records.

The close callback synchronously persists the exact full-set barrier and blocks scheduling, first prompts, retries, lease renewal and project context authority. In-flight preparation or missing final binding refuses a successful barrier ACK. The host revokes registration/browser/PTY authority and detaches fixed owned CLI sessions before acknowledging. It does not await outer RPCs from inside the barrier. Lost control channels persist a closed admission fence. No post-barrier failure rewrites the controller's closed snapshot.

This is an input-admission barrier, not proof that native tools or delegated/background processes have exited. The guardian subsequently drains and adopts/reaps its entire worker tree. Only its kernel ECHILD receipt proves that tree exited. External writers, publication and checkout cleanup require independent authority; this slice sets no `quiescedAt` and grants no cleanup.

## Validation

`HIVE_TEST_NATIVE_CODEX=1 node --test scripts/verify-codex-guarded-controller.test.mjs` composes the actual guardian, FD3 client, canonical controller/supervisor, pinned Codex 0.165, local mocked Responses, Git initialization, same-thread CLI and Python forkpty attachment. It exercises both direct and isolated native modes. The isolated case preserves the worker→bwrap→monitor→native lease chain and denies the native tool access to outer/controller keys, worker FD3 and worker environment. A synthetic agent credential is allowed only in the worker and absent from native tool environment.

The fixture independently verifies the signed preparation journal, refuses active-project drain, persists a synthetic closed-generation controller decision before the inner barrier, checks input denial and verifies all observed worker/native/wrapper/monitor/tmux/PTY processes disappear after ECHILD. Evidence records exact source digests and rejects changes during the test. A test-only output override, `HIVE_GUARDED_CONTROLLER_EVIDENCE_PATH`, stays beneath `guardian-local`; the isolated result uses a separate `-isolated.json` sibling.

Focused regressions cover closure while repository resolution/preparation/native ACK/manager ACK is pending, generation refresh across projects, closed project HTTP responses and all legacy controller/native progression tests. Fixture construction failures are retained in `guardian-local/controller-native-first-failure.json`; a partial marker-write race, generated string quoting and direct-only metadata bug were corrected before final evidence.

The composed proof injects synthetic lease inspection and controller admission/drain authorization. It does not exercise the fixed installed worker's private configuration startup, production controller barriers, startup challenge attestation, server receipt ingestion, remote Coder callbacks, source publication or account inference. These remain gates before installed activation.
