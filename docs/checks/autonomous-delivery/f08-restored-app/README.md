# F08 restored-data app and session rehearsal

On 2026-11-05 the reviewed 52c4b2e0 app/auth release archive ran locally in workerd against the isolated `hive_production_rehearsal_20261105` Neon database. This database contained the eight restored source tables and 88 original rows after 39 migrations. The original-column fingerprints matched the private read-only capture before the test, with the synthetic fixture present, and after cleanup. No original credential was decrypted and no live Coder API was called. The app was available only on loopback; this harness does not enforce a network-level egress sandbox.

A new role with no memberships, create or bypass privileges was scoped by row-level policies to a random synthetic user. The runner checked effective privileges, denial of dangerous table privileges, exact role/policy expressions and zero visibility of original rows before seeding. The app and auth Workers used an ephemeral cookie key, service key, encryption key and synthetic credential. They verified authenticated task access; rejection of a changed cookie signature, legacy cookie name, expired session, wrong encryption key and wrong service key; logout revocation; and the host-only secure logout cookie. Restricted fixture rows were removed, then owner cleanup locked and checked both validated cascade child relationships before deleting only the exact synthetic user. All original rows still matched.

`attempt1.json` and `attempt2.json` retain failed attempts and cleanup details. Attempt 3 succeeded and records artifact and source hashes. The dedicated role and its row policies were retained for separately reviewed cleanup; private connection material and checkpoints are not in this directory.

This is an application/session compatibility rehearsal against restored data. It does **not** prove production secret preservation, real legacy-session continuity, outbound network isolation, a deployment or cutover, R2/streaming behavior, or full F08 completion. The database contains production-derived data and must remain private. Any repetition requires the exact reviewed endpoint identity, owner-controlled private files, an independently reviewed plan and the fixed archive digest in the runner.
