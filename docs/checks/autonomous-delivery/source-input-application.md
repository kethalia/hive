# Protected accepted-source input barrier

This checkpoint provides a default-disabled local composition. It does not install
an application-authority factory, enable manager execution, authorize cleanup, or
claim that a kernel process tree is empty. The physical guardian/checkout writer
hold remains. The independent server application reservation and installed outer
journal verification are required before activation.

## Fixed composition

`createSourceApplication` in `codex-source-application.mjs` requires the installed
supervisor, controller, gateway, guardian application APIs, fresh factual source
state client, native source observer, and managed receipt inspector. The normal
worker entry launches only `/usr/bin/python3 -I` and the fixed sibling
`delivery-source-apply-worker.py`. Its environment contains fixed PATH and LANG;
no agent, owner, GitHub, or model credential is copied. Start frames carry four
identifiers (project, repository, application, publication operation), never paths,
commands, source bytes, or model-supplied authority.

The application requires one registered project in this native lifetime, exact
current claim/root/cohort, a completed root, and no attached manager CLI. It does
not interrupt another project to make an application possible. The supervisor
persists a closed input record before awaited work; the controller mirrors it.
Ordinary native calls, installed tool replies, CLI attachment, queued task advance,
and explicit execution admission remain fenced. A restart with an unresolved
supervisor record refuses new native launch; automatic restart recovery is not
implemented by this checkpoint.

The gateway closes only that project's terminal inputs, destroys their input
pipes, and waits for actual helper close events. A signal alone is not success.
The supervisor inspects the fixed private tmux inventory; unknown sessions hold.
It reads complete root and known-child history through a separate, fixed factual
read seam, drains the manager router, and compares the receive sequence. The
native observer must independently report the exact terminal, acknowledged cohort
and source operation. Browser history reads remain available. These observations
concern inputs and native facts, not detached background kernel writers.

## Durable records and lock ordering

`supervisor.projects[projectId].sourceApplication` and
`controller.projects[projectId].task.sourceApplication` contain the same operation,
application, target/prior source context, runtime/root/cohort, request digest,
closed barrier, unextended lease deadline, input inventories, native boundary,
source observer snapshot, and factual idle snapshot. The idle admission tuple
comes from fresh `guardian.currentMetadata`, never the first-native reservation.
No record embeds a digest of its own whole journal. The outer computes the two
journal digests independently.

The local phases are `closing`, `reserved`, `applied`, `committed`, `released`, or
`held`. Server authority phases remain `pending`/`applied`. A local metadata
receipt, `acceptedSource`, or local phase alone never releases inputs. Both local
source contexts are synchronized before `applyCommit`; a fresh positive
`applyVerify` readback is required afterward and again before terminal admission
release. Any unknown callback, helper, commit, or native outcome retains a hold.
Recovery may retry only the exact same operation and native lifetime; changed
identity is not adopted. `reserveAttempted` is durable before the first request.
An existing/ambiguous attempt is queried with `applyVerify` before proceeding;
absent, revoked, or unknown responses never justify re-reservation. The original
barrier, observation timestamp, idle snapshot, and source-observer facts remain
immutable. A separate `lastInputVerification` records a fresh native check only
after its history/inventory matches the original. An already-applied readback
skips another commit. Reconstructing the coordinator in the same live native
runtime is tested; launching a new native lifetime with a pending record refuses
before process creation.

The Python helper holds the managed lock while asking its parent for authority.
During that interval the controller's factual immutable checkout context uses
its signed application identity and captured, unextended active-lease deadline;
it does not reenter `managed.inspect`. This is not execution authority. Renewal
is deferred while the application is pending, but expiry still durably revokes
execution. The final applied callback runs after the helper releases the lock and
performs a fresh managed provenance/lease/source inspection.

Lease revocation has a separate installed-only stop seam. It requires durable
`executionRevoked` and exact existing application/root/mapped-child identity. It
can read bounded history and interrupt those exact turns, never start one.
Unknown threads retain review hold, repeated revocation does not release the
source application, and no stop receipt becomes cleanup authority.

## Protected objects and metadata

The worker reads only the existing operation under
`$HOME/.local/state/hive/delivery-source-publisher/broker/<operationId>`. It verifies
private ownership, HMAC scope and published phase, request/manifest/commit
identity, sealed bytes, config digest, and the pinned private Git directory.
It can read that immutable published operation while the publisher retains its
lifetime lock. It never initializes a store, republishes, fetches, or contacts a
provider. Object bytes are size-bounded and checked against Git object hashes.

The committed `managed-source-apply.py` remains responsible for expected-old
HEAD/index checks, two-tree index merge without `-u`, private recovery artifacts,
owned lock provenance, and immutable physical base/lease/incarnation. Worktree
bytes—including dirty, staged nonoverlapping, ignored, and untracked work—are
preserved. Its known interrupted candidate-index preparation gap retains a hold;
this checkpoint does not claim recovery at every instruction boundary.

## Evidence and remaining gate

The local evidence directory records exact source hashes and commands. Tests cover
real managed Git application through an actual private FD3 Python subprocess,
unchanged worktree bytes and staged edits, coordinator lost-ACK/revocation/late
input holds, terminal close/reconnect, bounded callback timeout and child reap,
controller lease expiry, and supervisor durable reads after input closure.
The pinned Codex 0.165 test uses a local canned Responses server only: the same
native thread remains readable while ordinary turn start is denied; the
revocation-only seam interrupts the actual active root, and an unmapped title
thread preserves its pre-existing review hold. No account inference or cloud
request occurs.

The coordinator tests inject explicit synthetic authority; the native test's
source records are an explicit fixture, not server-issued application authority.
A composed installed outer/server application proof, real source-state/producer
registration, package inclusion, and activation review are still required. The
factory has no automatic host/startup wiring in this checkpoint. There is no
kernel-quiescence, cleanup, production delivery, or end-to-end server claim.

The cross-language recovery regression also runs the actual JS coordinator and
private FD3 worker twice. It deliberately loses the first commit acknowledgement
after HEAD/index/managed receipt moved from physical base A to accepted B. On
retry, `apply_locked()` selects `sourceLastApplied.expected` and sends historical
`currentSource: null` (A's original context) through all callbacks; it does not
replace that expectation with current B. The real coordinator accepts that prior
identity. HEAD, index, and managed receipt bytes, inodes and modification times
remain unchanged on replay; one reserve, one commit, and one final release occur.
The fixture uses explicit synthetic server/producer authority and a task-private
managed checkout. Its test-only environment supplies fixture data to the Node
test runner, never to the installed worker entry or any production authority.
