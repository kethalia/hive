# Repository policy enrollment foundation (D08)

This slice removes per-task UUID policy configuration for enrolled repositories. It does not enable the deployment flag or authorize a provider write, native launch, release, cleanup, or semantic acceptance producer. Existing legacy task maps remain available only for tasks without a persisted binding while repository enrollment is disabled.

## Controller-owned contract

`HIVE_DELIVERY_REPOSITORY_POLICY_ENABLED=true` selects repository enrollment. `HIVE_DELIVERY_REPOSITORY_POLICIES_JSON` is a deployment-owned catalog (at most 32 entries / 256 KiB). Each entry binds the Hive owner UUID, GitHub numeric repository/account IDs, exact canonical full name, source-publication restrictions, mandatory GitHub workflow/app/reviewer selectors, and reviewed acceptance contracts. Neither browser task fields nor model task metadata can choose a policy or version.

The ordinary authenticated task-start path first resolves the repository through the existing signed owner/build-bound host helper using that agent's own GitHub authentication. Enrollment checks its fresh stable identity, canonical full name, non-archived status, and pull/push permission against the catalog. New owner intent insertion and its immutable policy version/digest/exact UTF-8 intent digest share a Serializable transaction. The encrypted owner prompt retains the existing lifecycle; this slice stores no additional prompt plaintext. Duplicate acknowledgement preserves the original pin. A later execution/retry/reconciliation reauthorizes the pinned version; acknowledgement itself is not execution permission. Once a project is enrolled, flag-off cannot create a new legacy/unbound intent or reuse an older unbound task. The intent INSERT trigger locks the project against concurrent enrollment, so this check is transactional rather than a feature-flag race.

The manager's distinct delivery-task ID inherits the preparation intent's version in the same transaction as task/step creation. The binding includes the immutable physical source base, exact outcome digest, complete compiled repository gates, and per-step acceptance links/pending requirements. Source publication and GitHub evidence adapters consult this persisted binding before legacy selectors. Disabling the flag cannot restore legacy authority for an already-bound task. Unknown tasks under the enabled selector fail closed.

Activation changes affect new intents only. Explicit `RepositoryPolicyStore.revokeVersion` fences existing pinned tasks; reenrolling unchanged revoked catalog content is refused. A newly approved catalog revision can create a new immutable version. Removed catalog entries block new enrollment but do not implicitly revoke previous versions. Revocation has no public/model API in this slice. It intentionally stops all manager mutations, including informational reports and failure reports, rather than introducing an exception that could alter scheduling. Native forensic ingestion and factual history remain separate; no writer hold is cleared. Repository/account/full-name drift is a hold; there is no automatic identity adoption or reparenting.

## Repository gates versus task meaning

Every repository check/review criterion uses the reserved `repo:` namespace. The manager cannot select those identities as task criteria, remove them by choosing an informational step, or omit required groups from completion. Trusted transport derives the extra reserved criteria from the persisted policy and rechecks them in the publication transaction; the collector request cannot supply an allowance. Evidence ingestion retains the existing exact PR/head, workflow/app/reviewer provenance, full group watermarks, invalidation, phase quality, and freshness checks. PR number comes from the independently accepted source revision, never a model PR assertion or per-task environment map.

Reviewed acceptance links match exact owner-intent digest, task-outcome digest, criterion ID/meaning digest, and complete evaluator selector. Matching these fields is **not proof of semantic acceptance**. The current GitHub snapshot ABI does not attest immutable evaluator workflow/script content or a scoped intent-aware independent decision. A matching link is stored with `evaluationState: awaiting_independent_producer` and `acceptance_evaluator_provenance_pending`; an unmatched meaning has `acceptance_evaluator_unavailable`. Neither condition is converted to a pass by successful ordinary CI or a generic Codex review.

Completion and subsequent claim authorization independently check all current repository gates and then retain the semantic hold. A factual status response reports pending acceptance, with execution/publication/cleanup flags false. Bounded current-claim collection may continue gathering prerequisite repository evidence while semantic acceptance is pending; it keeps the existing once-per-minute limit, revocation/pause checks, and fixed challenge scope. No additional writes or provider selectors are introduced.

This is a foundation, not a generally autonomous acceptance solution. Next work must add an independently authenticated evaluator receiving immutable original intent, exact criterion semantics, candidate SHA/diff, and current check evidence, and persisting a structured scoped decision with producer/model/code provenance. A pilot may instead use a separately verified immutable external/base-pinned evaluator. No catalog boolean may substitute for that provenance. The resulting decision is defensible review evidence, not a formal correctness claim.

## Persistence and concurrency

Migration 30 adds `delivery_repository_policies`, immutable `delivery_repository_policy_versions`, and immutable `delivery_task_policy_bindings`, plus an all-or-none nullable policy pin on `project_task_intents`. Existing rows stay unbound. Owner/project composite foreign keys, generation monotonicity, active-version monotonicity, no-retroactive-intent-adoption triggers, immutable task projections, complete digest verification, bounded JSON, and retained history are enforced. Runtime role grants are SELECT/INSERT/UPDATE only; PUBLIC and runtime DELETE/TRUNCATE/REFERENCES/TRIGGER authority are explicitly excluded. Existing triggers further reject unauthorized content replacement.

Lock order is project → policy → version inside the surrounding owner/registration/task transaction. Exact version row locking prevents a stale Serializable waiter from accepting a concurrently revoked version. Full immutable bindings are reread/recomputed at action time; a policy version label alone is not authority. The SQL's 72 KiB serialized JSON ceiling allows PostgreSQL JSONB whitespace around the application's stricter 64 KiB canonical policy/binding ceilings.

Source publication binds the complete policy before CI for the new commit exists. It does not require impossible pre-publication CI. Successful repository/evaluator evidence is required at completion/continuation. The physical writer anchor and original checkout source base remain unchanged; no quiescence or cleanup permission is added.

## Remaining onboarding and pilot gates

1. Deploy the reviewed catalog/selector and migration only after independent review. No flag is changed by this slice. Catalog installation is the operator's policy approval; normal users then provide a task without task UUID configuration.
2. Nondefault base refs currently return `repository_policy_ref_resolution_pending`. Existing host resolution supplies only `defaultRevision`; selecting `codex/epic` as PR base must not pretend the checkout used that ref. A fixed policy-derived ref resolution path must be implemented and verified before an epic-branch pilot.
3. Complete the independent acceptance producer or verified external evaluator integration above. With the current foundation, semantic completion intentionally remains pending.
4. Refresh installed runtime identity/model/authentication and exact guardian/package policy before the separately authorized test-workspace pilot. This source slice performs no live Coder, GitHub, cloud, or account-inference action.

## Validation and limitations

`repository-policy-local/result.json` records exact source hashes and final commands/results. The local migration probe upgrades synthetic schema-29 rows to schema 30, verifies all 39 prior tables' projected contents and all migration checksums remain unchanged, confirms the legacy intent pin is null, and verifies actual restricted-role SELECT and denied DELETE. A prior probe omitted the non-timestamp `0_init` directory; that fixture construction failure is retained and the final probe includes it explicitly.

Real PostgreSQL tests cover owner/account/version binding, atomic encrypted enqueue, SQL immutability/null/FKs, no fallback after enrollment, unchanged-revoked catalog refusal, activation versus old intents, concurrent enrollment and revoke/writer races. Signed manager/native/source/GitHub transport tests use real controller persistence and guardian lifecycle plus explicit local publication/provider artifact doubles. They prove missing repository review and pending semantic acceptance block both completion and attempted subsequent claims; cursor/attempt counts and physical holds remain unchanged. They do not claim real provider evaluation or account-backed inference.

The fresh schema-to-Prisma comparison has no D08 difference. It retains the existing two SQL-only guardian/registration foreign keys and existing project-intent FK-name discrepancy; this slice does not drop or rename those constraints. No hosted migration or runtime activation occurred.
